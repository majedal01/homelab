# CLAUDE.md

Working conventions for this repo. They apply to every change. Read them before each
task.

## What this repo is
The infrastructure for a personal homelab: Proxmox host, VMs, the public edge, and the
reusable deploy workflow that application repos call. Applications live in their own
repos and are not in scope here. It should read and run like real infrastructure.

## Layout
`hosts/<host>/` holds one machine's config with a README and, where the host is
scripted, an `apply.sh`. `.github/workflows/` holds the reusable deploy plus this repo's
media CI and deploy. Naming in `docs/conventions.md`, deploy contract in
`docs/deployment.md`, topology in `docs/network.md`.

## Hosts
Never run a command against the Proxmox host, a VM, or the edge unless the task is
about that host and the user has asked. Reading state over SSH is fine. Config changes
go through the files under `hosts/` and that host's `apply.sh`.

## Deployment
Trunk-based: branch off `main`, open a PR, pass CI, merge. Never push to `main`. The
media stack deploys by a manual run of `media-deploy.yml`. Application repos deploy
themselves through `deploy.yml`; merge auto-deploys their stage, prod is a manual run.

## Commits and PRs
A commit or PR is written by the developer and documents the change and why it exists.
It never mentions the request, the conversation, or a person who asked. Phrases like
"per your request", "as requested", "based on your request", "as you asked", or "per
our discussion" do not belong in version history. State the change, not who wanted it.

Commits:
- Format `type(scope): summary`, imperative mood, lowercase, no trailing period. Types:
  feat, fix, refactor, docs, chore, tune, deploy. Scope optional (`fix(media):`).
- Subject under ~70 characters. Add a body only when the diff doesn't speak for itself;
  wrap at ~72 and explain why, not what.
- No first person ("I added", "we decided"), no emoji, no co-author or "generated by" trailers.
- One logical change per commit.

PRs:
- Open with two or three plain sentences: what changed and why. Then what a reviewer
  needs (behavior changes, how it was verified). Everything else follows the
  documentation rules below.
- A test plan lists what you actually ran. Check a box only after running that step.

Before executing, show the commit sequence and wait for confirmation.

## Code
Shell scripts and compose files, mostly. Plain naming, `set -euo pipefail`, comments
explain why and never what. No premature abstraction. Match the style of the file you
are editing. LF line endings everywhere; `.gitattributes` enforces it.

## Documentation
Write so it reads as if a person wrote it in a hurry but knew the system. This is
enforced, not a preference.

- Keep it short. A README is a page, not a manual. If a line restates the obvious, cut it.
- Plain prose, plain hyphens. No em dashes. No emoji. No Title Case headers.
- Minimal formatting. Bold and bullets only when they earn it. Never bold for emphasis
  inside a sentence.
- No marketing voice. Drop "powerful", "seamless", "robust", "comprehensive", "simply",
  "just". Say what it does.
- No filler ("it's worth noting", "importantly", "as mentioned") and no closing summary
  that repeats the section above.
- Uneven is fine. Do not pad for symmetry or parallelism.
- Document what exists. No roadmap padding, no aspirational features written as present.
