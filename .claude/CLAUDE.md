# CLAUDE.md

Working conventions for this repo. They apply to every change, in every app. Read
them before each task.

## What this repo is
A personal homelab monorepo. Each app runs on owned hardware with production-grade
practices: trunk-based CI/CD, dev/stage/prod environments, observability,
infrastructure as code. It should read and run like real infrastructure, not a demo.

## Layout
Apps live at `apps/<domain>/<app>/`, grouped by domain. A new app is a new directory under
its domain; a new domain is a new top-level folder. Structure, naming, and namespacing are
in `docs/CONVENTIONS.md`.

## Stack (defaults; apps may differ)
- Backend: Python 3.12+, FastAPI, Pydantic; pytest + httpx; Ruff for lint and format,
  mypy for types
- Frontend (when present): Next.js App Router, TypeScript, Tailwind
- Docker and Docker Compose; GitHub Actions for CI/CD; ghcr.io for images

Do not assume a database. State each app's storage choice in its own README; some apps
are stateless by design.

## Deployment
Trunk-based: branch off `main`, open a PR, pass CI, merge. Never push to `main`. Merge
auto-deploys stage; prod is a manual `deploy-prod` workflow run against `main`; `dev` runs
locally from `deploy/dev/`. Per-app workflows call the reusable `deploy.yml`. Flow, VM
layout, and secrets are in `docs/deployment.md`.

## Commits and PRs
A commit or PR is written by the developer and documents the change and why it exists.
It never mentions the request, the conversation, or a person who asked. Phrases like
"per your request", "as requested", "based on your request", "as you asked", or "per
our discussion" do not belong in version history. State the change, not who wanted it.

Commits:
- Format `type(scope): summary`, imperative mood, lowercase, no trailing period. Types:
  feat, fix, refactor, docs, chore, test, tune, deploy. Scope optional (`fix(insights):`).
- Subject under ~70 characters. Add a body only when the diff doesn't speak for itself;
  wrap at ~72 and explain why, not what.
- No first person ("I added", "we decided"), no emoji, no co-author or "generated by" trailers.
- One logical change per commit.

PRs:
- Open with two or three plain sentences: what changed and why. Then what a reviewer
  needs (behavior changes, migration notes, how it was verified). Everything else follows
  the documentation rules below.
- A test plan lists what you actually ran. Check a box only after running that step.

Before executing, show the commit sequence and wait for confirmation.

Example. Bad: `docs: updated the README per your request to make it shorter`.
Good: `docs(readme): trim setup to a page`.

## Code
- Idiomatic, type-hinted Python. Plain naming, reasonable function size.
- Comments explain why, never what. None when the code is obvious.
- No premature abstraction. Build what the task needs.
- Match the style of the file you are editing.

## Documentation
Write so it reads as if a person wrote it in a hurry but knew the system. This is
enforced, not a preference.

- Keep it short. A README is a page, not a manual. A design doc is the decisions and
  the tradeoffs and nothing else. If a line restates the obvious, cut it.
- Plain prose, plain hyphens. No em dashes. No emoji. No Title Case headers.
- Minimal formatting. Bold and bullets only when they earn it. Never bold for emphasis
  inside a sentence.
- No marketing voice. Drop "powerful", "seamless", "robust", "comprehensive", "simply",
  "just". Say what it does.
- No filler ("it's worth noting", "importantly", "as mentioned") and no closing summary
  that repeats the section above.
- Uneven is fine. Real notes have a list of two and a list of nine. Do not pad for
  symmetry or parallelism.
- Document what exists. No roadmap padding, no aspirational features written as present.
